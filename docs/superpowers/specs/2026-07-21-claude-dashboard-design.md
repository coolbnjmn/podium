# Claude Usage Dashboard — Design

Date: 2026-07-21

## Purpose

A locally-run dashboard, kept open in a browser tab while developing, that visualizes:

1. **Claude Code (Pro/Max) usage** — derived from local session transcripts, since Anthropic does not expose an official usage/limit API for Claude.ai Pro/Max plans.
2. **Anthropic API usage & cost** — pulled from the Anthropic Admin Usage & Cost API, using an org Admin API key.

The goal is to help the user judge, at a glance, whether they're trending toward needing to spend more (upgrade plan / add API budget).

## Non-goals

- No official "% of Pro/Max weekly limit" — Anthropic does not expose that number via any API. The dashboard shows raw usage trends (tokens, messages, sessions) instead, clearly labeled as an estimate.
- No multi-user / hosted deployment. Single local user, local filesystem access, local `.env` secret.
- No historical data older than what's retained in `~/.claude/projects/**/*.jsonl` (Claude Code's own retention) or what the Admin API returns.

## Architecture

```
claude-dashboard/
├── server/                  Node/Express backend (TypeScript)
│   ├── index.ts              boot: start HTTP server, serve API + built frontend
│   ├── claudeCode.ts          scan ~/.claude/projects/**/*.jsonl, aggregate
│   ├── adminApi.ts            call Anthropic Admin Usage/Cost API
│   ├── cache.ts               in-memory TTL cache for both data sources
│   └── routes.ts              GET /api/claude-code, GET /api/api-usage
├── frontend/                 Vite + React (TypeScript)
│   └── src/
│       ├── App.tsx
│       ├── components/        StatTile, TimeSeriesChart, ModelBreakdown, ProjectBreakdown
│       ├── hooks/usePolling.ts
│       └── theme/             dark-mode palette (per dataviz skill)
├── .env                       ANTHROPIC_ADMIN_API_KEY=... (gitignored, never sent to browser)
└── package.json                root scripts (concurrently runs server + frontend dev servers)
```

The backend is the only thing that talks to the filesystem and the Admin API. The frontend only talks to the local backend over `localhost`, polling on an interval. This keeps the Admin API key server-side only.

## Data source 1: Claude Code / Pro-Max usage (local logs)

**Source:** `~/.claude/projects/**/*.jsonl` — one file per session, one JSON object per line (assistant messages, user messages, tool calls, etc).

**Relevant fields** (from assistant-message lines):
- `message.usage.input_tokens`, `.output_tokens`, `.cache_creation_input_tokens`, `.cache_read_input_tokens`
- `message.model`
- `timestamp` (ISO 8601)
- `cwd` (local project directory — used for the per-project breakdown)
- `sessionId`

**Aggregation (computed server-side, cached, re-scanned periodically):**
- Daily totals: tokens (split input/output/cache) per day, last 30 days
- Per-model totals: tokens per model (Opus/Sonnet/Haiku/etc), last 30 days
- Per-project totals: tokens per `cwd`, last 30 days
- Today / this week / this month rollups for the KPI tiles

**Refresh:** re-scan on every backend cache-refresh cycle (every 60s) — cheap enough since it's just reading local files; only re-parses files modified since the last scan (mtime-based incremental scan) to keep this fast as history grows.

## Data source 2: Anthropic API usage & cost (Admin API)

**Source:** Anthropic's Admin Usage & Cost Reporting API, authenticated with an **Admin API key** (`sk-ant-admin-...`), generated by an org admin in the Anthropic Console. Stored in a local `.env` file (`ANTHROPIC_ADMIN_API_KEY`), read only by the backend.

**Aggregation (cached, refreshed every ~5 minutes to avoid hammering the API):**
- Daily token usage per day, last 30 days
- Daily $ cost per day, last 30 days
- Per-model breakdown (tokens + $)
- Today / this week / this month $ rollups for the KPI tiles

Exact endpoint paths and response shapes will be confirmed against live Anthropic documentation during implementation (this API surface changes independently of the Messages API and isn't in the assistant's bundled reference material) — implementation will not guess field names without verifying first.

**Missing/invalid key:** if `ANTHROPIC_ADMIN_API_KEY` is unset or the Admin API call fails (401/403), the API-usage panel shows a clear "not configured" state rather than blocking Claude Code data from displaying.

## API endpoints (backend → frontend)

- `GET /api/claude-code` → `{ daily: [...], byModel: [...], byProject: [...], today, week, month }`
- `GET /api/api-usage` → `{ daily: [...], byModel: [...], today, week, month, configured: boolean }`

Both cached server-side; each call returns the cached snapshot immediately (no per-request scan/API call).

## Frontend layout

Dark mode only (per user request), following the dataviz skill's color/contrast rules and frontend-design skill for typography/layout polish.

1. **KPI stat-tile row** (top): Today / This week / This month — each tile shows Claude Code token volume and API $ spend side by side.
2. **Usage trend chart**: multi-line time series, last 30 days — Claude Code tokens/day and API $/day (dual-axis or two stacked mini-charts, decided during implementation based on how the two scales compare visually).
3. **Model breakdown**: two donut/bar charts (Claude Code tokens by model, API $ by model) side by side.
4. **Project breakdown**: horizontal bar chart, top local project directories by Claude Code token volume.

All charts use the palette and contrast rules from the dataviz skill's `references/palette.md`, adapted for a dark background.

## Refresh & run model

- Backend: re-scans local logs every 60s, re-fetches Admin API every ~5min, both cached in memory.
- Frontend: polls backend `/api/*` endpoints every 30–60s (auto-refresh, no user action needed).
- Run: `npm run dev` from the repo root starts backend + frontend dev servers together (via `concurrently`); user opens `http://localhost:<port>` and leaves the tab open.

## Error handling

- Local log scan errors (malformed JSONL lines) are skipped per-line, not fatal to the whole scan.
- Admin API errors surface as a "not configured / unreachable" state in that panel only — the Claude Code panel keeps working independently.
- No user-facing crash on missing `.env` — the app boots and shows setup instructions for the Admin key if absent.

## Testing

- Backend: unit tests for the JSONL aggregation logic (given sample transcript lines, verify daily/model/project rollups) and for Admin API response parsing (given sample response shapes).
- Frontend: manual verification in-browser (per the UI testing guidance — start the dev server, check charts render correctly in dark mode with real local data).
